# セキュリティ要件と検証方法のたたき台

## 状態と適用範囲

要件・設計段階からセキュリティを考慮するシフトレフト方針です。以下の「決定済み」は採用する方針を意味し、対策の実装完了を意味しません。秘密情報検査の実装・検証状況は次節のとおりです。それ以外の検証は未実施です。

サービスの題材、データ、認証方式、公開方法が未決定のため、個別対策は提案として整理します。秘密情報検査以外の検査ツール・コマンド・合否基準、証跡の保存先・期間は未決定です。

SEC-05・06・11 のうち Git への混入防止を対象としています。イメージへの混入防止、依存関係検査、イメージ検査、SBOM、Terraform / AWS の実環境での保護は未実装・未検証です。

検証コマンドは `python scripts/secrets.py files`、`python scripts/secrets.py staged`、`python -I scripts/test_secret_controls.py` です。本リポジトリのステージは空なので、staged の検出なしだけでは検証済みとせず、現在のファイルを複製した隔離リポジトリで実際のフックを検証しました。一時リポジトリは終了時に削除し、本リポジトリの index・HEAD が変わっていないことも確認しました。本リポジトリにはコミットがなく、その履歴検査は未実施です。

詳細な再現手順と push 後の確認項目は [開発環境](development.md)を参照してください。Gitleaks はパターン検査であり、任意の秘密情報をすべて発見できる保証はありません。Gitignore やローカルフックだけで混入防止が強制されるわけではないため、CI の必須チェック設定も別途必要です。

## 要件・設計で確認すること（提案）

- 資産：利用者データ、認証情報、DB、ソース、イメージ、AWS 権限、Terraform の状態ファイル。
- 境界：ブラウザーとアプリ、アプリと DB、GitHub Actions と AWS、外部公開部分と内部ネットワーク。実際の構成決定後に図とデータフローを記録する。
- 脅威：不正入力、権限のない閲覧・変更、秘密情報の漏えい、依存関係の脆弱性、過剰な権限、公開設定の誤り、資源の大量消費。
- 各脅威に、対象要件、対策、検証方法、残るリスクを対応付ける。不要な個人情報を収集しない設計を検討する。

## 決定済み方針と検証案

検証方法・タイミングは以下をたたき台に具体化します。

| ID | 決定済みの方針 | 検証方法案・残す証跡 |
| --- | --- | --- |
| SEC-01 | 要件・設計からセキュリティを考慮する | 実装前と設計変更時にデータ・権限・信頼境界・脅威をレビューし、要件と検証ケースの対応を残す |
| SEC-02 | 必要最小限のベースイメージを使う | Dockerfile と最終イメージのパッケージを確認し、実行に必要なものと選定理由を記録する。容量の小ささだけで選ばず、互換性・更新可能性も確認する |
| SEC-03 | 非 root ユーザーで実行する | Dockerfile の USER と ECS 実行設定を確認し、起動したコンテナの実効 UID が 0 でないこと、必要な読み書きと起動が成功することを確認する |
| SEC-04 | マルチステージビルドを採用する | ビルド用と実行用の段階を確認し、最終イメージに不要なビルドツールやキャッシュがないことを調べ、起動確認を行う |
| SEC-05 | 秘密情報を Git・イメージに含めない | Git の変更と履歴、ビルドコンテキスト、イメージのレイヤー・設定を検査する。除外設定だけでなく検出結果を確認し、ログにも実値を残さない |
| SEC-06 | 秘密情報検出を工程に組み込む | ローカルと PR での検査を設計する。検査対象範囲を記録し、隔離した検証用のダミー文字列で検出・失敗終了を確かめる。実際の秘密情報は使わない |
| SEC-07 | 依存関係検査を工程に組み込む | フロント・バック両方の依存関係とロックファイルを検査し、対象・検査日時・検出結果を保存する。定期的な再検査の頻度を決める |
| SEC-08 | イメージ検査を工程に組み込む | ビルドした配布対象イメージを検査し、ダイジェストと OS・言語パッケージの検出結果を記録する。検査対象とデプロイ対象の一致を確認する |
| SEC-09 | SBOM を生成する | 配布対象イメージに対応する SBOM を生成し、アプリと OS の構成要素が対象に含まれるか確認する。形式、対象ダイジェスト、生成日時を記録する |
| SEC-10 | Terraform の権限・ネットワーク・状態保護を検討する | 下記のインフラ検証案を設計に反映し、設定レビュー、IaC 検査、plan と構築後の確認を行う |
| SEC-11 | テスト・検査を無効化して成功扱いにしない | 必須ジョブと失敗伝播をレビューし、失敗を発生させる制御された検証でマージ・デプロイを止められるか確認する。未実行や検査エラーも合格としない |

SBOM は構成要素の一覧であり、生成できたこと自体を脆弱性がない証明とはしません。

マルチステージによるビルド環境と実行環境の分離は [Docker 公式のビルド指針](https://docs.docker.com/build/building/best-practices/)を参照します。ビルド時に秘密情報が必要な場合は、ARG / ENV や COPY に埋め込まず、[Docker の secret mount](https://docs.docker.com/build/building/secrets/)を検討します。

## 工程への組み込み案

1. **要件・設計**：データ、脅威、権限、受け入れ条件、検査の合否基準を整理する。
2. **実装・PR**：関連する自動テスト、秘密情報・依存関係・IaC の検査、設計レビューを実施する。
3. **イメージ作成・公開前**：最終イメージの非 root 起動、イメージ検査、SBOM 生成と対象の一致を確認する。必須チェック通過を公開条件にする。
4. **公開後・依存関係更新時**：脆弱性の再検査、権限・ログの確認、更新・復旧の検証を行う。頻度は未決定。

## 合否・証跡・検出時の対応

- **決定済み**：失敗・未実施を成功扱いにしない。テストや検査を無効化して通さない。
- **秘密情報検査で決定済み**：Gitleaks 8.30.1 の既定ルールを使用し、1 件以上の検出で失敗する。検査エラーも失敗とし、全秘密値を伏せる。インラインの `gitleaks:allow` による除外は許可しない。現在は独自 allowlist・baseline を設定していない。
- **未決定**：秘密情報検査以外の検査ツール、脆弱性の重大度・修正可能性に応じた停止基準、追加の必須チェック、定期実行頻度、証跡の保存先・期間。GitHub の `Gitleaks` 必須チェック登録は未設定・未検証。検査導入時に基準を明文化し、基準未決定の状態を公開可能とみなさない。
- **提案**：検出内容を調査し、修正して同じ検査を再実行する。誤検知なら根拠・対象・確認者・期限を記録し、除外はその対象に限定する。検査全体の停止や、都合のよい基準変更で解消扱いにしない。
- **提案**：検証結果には要件 ID、対象コミットまたはイメージダイジェスト、実行環境、ツール・ルールのバージョン、日時、結果、対応内容を記録する。証跡に秘密情報を含めない。
- **提案**：秘密情報の漏えいが判明した場合は、対象を失効・再発行し、影響範囲とログ・履歴・イメージへの混入を調査する。ファイルを削除しただけで解決扱いにしない。

この文書は検証計画です。テストやスキャンで確認できる範囲と、レビューや実環境での確認が必要な範囲を区別し、完全な安全性を保証するものとして扱いません。
