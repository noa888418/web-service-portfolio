# 社内IT依頼・改善管理サービス：初期版の要件案

## 状態と目的

**題材「社内IT依頼・改善管理サービス」は決定済みです。** 以下の利用者、機能、権限、遷移、上限、受け入れ条件、対象外の範囲は、すべてレビュー対象の提案です。承認済みの仕様や実装済みの機能として扱いません。アプリの実装・検証は未実施です。

開発環境の秘密情報検査は実装・ローカル検証済みです。GitHub Actions の**初回 push に対する検査成功は利用者確認済み**です。実行 URL・対象 SHA・詳細ログは未提示で、こちらでの直接確認はしていません。PR の検査、CI での検出時の失敗、必須チェック設定は別途確認が必要です。

目的は、小規模な Web サービスを完成させ、利用者の課題から設計・実装・検証までのつながりを面接で説明できるようにすることです。共通の決定事項は [README](../README.md)、セキュリティの詳細は [security.md](security.md) を参照します。

## 対象利用者・業務課題・シナリオ（提案）

単一の会社内で使うサービスとし、複数会社の契約・テナント管理は対象外とします。これは業務上の想定であり、AWS 上での公開範囲やネットワーク方式を決定するものではありません。ポートフォリオの初期データには架空の会社・利用者・依頼のみを用います。

| 利用者 | 想定する課題 | 提供する価値 |
| --- | --- | --- |
| 社員 | 問い合わせや不具合報告が口頭・チャットに散らばり、進捗や回答の確認先が分からない | 自分の依頼とやり取りを一か所で確認できる |
| IT担当者 | 担当者や対応状況が曖昧になり、未着手の依頼が埋もれる | 全依頼の受付、担当割り当て、対応状況の更新ができる |

1. 社員がログインし、タイトル・内容・種別を入力して依頼を登録する。初期状態は「未対応」、担当者なし。
2. IT担当者が一覧から依頼を開き、自分または別の IT担当者を割り当て、「対応中」にする。
3. 依頼した社員と IT担当者がコメントで状況や対応内容を共有する。
4. IT担当者が「確認待ち」にし、社員が確認結果をコメントする。追加対応が必要なら IT担当者が「対応中」に戻し、解決と判断したら「完了」にする。
5. 完了後は一覧・詳細を参照できる。追加の相談は新しい依頼として登録する。

## 初期機能と要件 ID（提案）

| 要件 ID | 機能 | 初期版の範囲 |
| --- | --- | --- |
| FR-01 | ログイン | 初期アカウントでメールアドレスとパスワードを使ってログインする。セッション等の実現方式は未決定 |
| FR-02 | ログアウト | 現在のログイン状態をサーバー側でも無効にし、保護された情報へ再アクセスできなくする |
| FR-03 | 依頼登録 | 社員が自分の依頼を登録する。依頼者・初期状態・作成日時はサーバーが設定する |
| FR-04 | 依頼一覧 | 社員は自分の依頼のみ、IT担当者は全依頼を閲覧。ID、タイトル、種別、依頼者表示名、担当者表示名（未割当を含む）、状態、作成日時を表示する |
| FR-05 | 依頼詳細 | 一覧の項目に加え、内容・更新日時・コメントの本文、投稿者表示名、投稿日時を表示する。コメントの公開範囲は依頼と同じ |
| FR-06 | 担当者割り当て | IT担当者が担当者を 1 人選択・変更する。担当候補は IT担当者のみ。解除は「未対応」の間のみ |
| FR-07 | ステータス変更 | IT担当者が下記の遷移表に従って状態を変更する |
| FR-08 | コメント投稿 | 依頼した社員と IT担当者が、完了前の依頼に投稿する。内部向け非公開コメントは設けない |
| FR-09 | 初期データ投入 | 開発・検証用アカウントと架空の依頼・コメントを環境準備時に投入する。Web 画面からは実行不可 |

一覧は作成日時の降順・同時刻は ID の降順で固定し、1 ページ 20 件とします。コメントは投稿日時の昇順・同時刻は ID の昇順で、1 ページ 20 件とします。一覧の件数・ページ情報も閲覧可能な範囲だけから算出します。検索・絞り込み・並べ替え UI は初期版に含めません。

## 対象外と、明示的に提供しない操作（提案）

| 対象外 | 初期版での扱い・理由 |
| --- | --- |
| 添付ファイル、メール通知、複雑な承認フロー、ダッシュボード | 基本の受付から完了までに絞り、ファイル保管・外部配信・承認機構を増やさない |
| ユーザー管理画面、一般向け新規会員登録、役割変更 | 初期アカウントのみ。IT担当者はユーザー管理者ではなく、社員・IT担当者の両方とも Web 経由でアカウント・役割を変更できない |
| パスワード変更・自己再発行、SSO・MFA | 初期版の画面機能には含めない。資格情報の紛失・失効対応は公開前の運用検討事項として残す |
| 依頼の編集・削除・取り下げ、依頼者変更 | 登録後のタイトル・内容・種別は変更しない。完了前の訂正はコメントで補足する。削除ボタン・削除 API を設けない |
| コメントの編集・削除 | 投稿後は変更しない。完了前なら新たなコメントで訂正する |
| 完了後のコメント・担当変更・再開 | 完了は参照専用。追加対応は新しい依頼で行う。依頼間の専用リンク機能は設けず、必要なら本文に旧依頼 ID を記す |
| IT担当者による依頼登録、社員による状態変更・担当指定 | 役割を単純に分ける。兼務・複数役割・代理登録は設けない |
| 優先度・期限・タグ、検索・絞り込み、変更履歴画面 | 初期版に追加しない。運用ログの保護は別途セキュリティ要件として扱う |

提供しない操作を、隠れた API や汎用更新処理から実行できる状態にしません。業務画面に削除を設けないことと、保存期限到来・誤投入時の運用上の削除方針は分けて検討します。

## 操作権限表（提案）

各アカウントの役割は社員または IT担当者のいずれか 1 つです。「自分」はログイン中の本人が依頼者であることを意味します。IT担当者は自分が割り当てられていない依頼も対応できます。

| 操作 | 未認証 | 社員 | IT担当者 |
| --- | --- | --- | --- |
| ログイン（FR-01） | 初期アカウントで可 | 可 | 可 |
| ログアウト（FR-02） | 無効な認証状態のまま終了 | 自分のログイン状態のみ | 自分のログイン状態のみ |
| 依頼登録（FR-03） | 不可 | 自分の依頼のみ | 不可 |
| 一覧・詳細・コメント閲覧（FR-04・FR-05） | 不可 | 自分の依頼のみ（完了を含む） | 全依頼（完了を含む） |
| 担当候補の取得・割り当て・変更（FR-06） | 不可 | 不可 | 完了前のみ。担当候補は IT担当者の ID・表示名だけを返す |
| 担当解除（FR-06） | 不可 | 不可 | 未対応のみ |
| ステータス変更（FR-07） | 不可 | 不可 | 遷移表の範囲のみ |
| コメント投稿（FR-08） | 不可 | 自分の依頼・完了前のみ | 全依頼・完了前のみ |
| 初期データ投入（FR-09） | Web 経由不可 | Web 経由不可 | Web 経由不可（環境準備の実行者だけが別手順で実施） |
| 編集・削除・役割変更・完了後の再開 | 不可 | 不可 | 不可 |

認証された利用者・保存済みの役割・依頼者との関係を用い、**すべての操作をサーバー側で認可**します。画面での表示制御だけに依存しません。クライアントが送る利用者 ID、役割、所有者条件を認可根拠として信用しません。

## ステータスと遷移（提案）

| 状態 | 意味・条件 |
| --- | --- |
| 未対応 | 登録済み・対応開始前。担当者なし、または割り当て済み |
| 対応中 | IT担当者が対応中。担当者必須 |
| 確認待ち | 対応内容を提示し、依頼者の確認を待つ。担当者必須 |
| 完了 | IT担当者が解決と判断。担当者を保持し、以後参照専用 |

| 遷移元 | 遷移先 | 変更できる人・条件 |
| --- | --- | --- |
| 新規登録 | 未対応 | FR-03 の登録成功時にサーバーが設定。社員は初期状態を指定できない |
| 未対応 | 対応中 | IT担当者。担当者が割り当て済み |
| 対応中 | 確認待ち | IT担当者。担当者が割り当て済み |
| 確認待ち | 対応中 | IT担当者。追加対応が必要と判断したとき。担当者を保持 |
| 確認待ち | 完了 | IT担当者。解決したと判断したとき。担当者を保持 |

表にない遷移（未対応から完了、対応中から未対応、完了からの再開など）は拒否します。同じ状態への変更要求も受け付けません。割り当て・コメントで状態は自動変更しません。

通常は確認待ちで社員がコメントを返し、IT担当者が完了を判断します。ただし初期版では、社員の承認ボタンや確認コメントの必須判定は設けません。技術的な完了条件は「IT担当者・確認待ち・担当者あり」とし、この簡略化が業務に合うかレビューします。

担当者・状態の更新では古い画面からの変更で上書きしないよう、読み取り時点の版などで競合を検出し、競合時は再読込を促します。方式は設計時に選定します。コメントと完了が同時に実行された場合も、サーバーで確定した順序に従い、完了後に確定する投稿を拒否します。

## 入力項目と上限（提案）

| 対象 | 入力 | 必須条件・上限案 |
| --- | --- | --- |
| FR-01 | メールアドレス | 必須、メール形式、最大 254 文字。前後空白を除去し、小文字に統一して初期アカウントと照合 |
| FR-01 | パスワード | 必須、1～128 文字の入力を受付。前後空白や大文字小文字を変更しない。これは照合時の入力上限であり、初期資格情報の強度基準は別途決める |
| FR-03 | タイトル | 必須、前後空白除去後 1～100 文字、改行不可 |
| FR-03 | 内容 | 必須、前後空白除去後 1～5,000 文字、改行可 |
| FR-03 | 種別 | 必須。「問い合わせ」「不具合」「改善要望」のいずれか 1 つ |
| FR-06 | 担当者 ID | 割り当て・変更時は既存 IT担当者の ID 必須。未対応時の解除に限り null 可。社員・不存在の ID は不可 |
| FR-07 | ステータス | 必須、定義済み 4 状態のいずれか。さらに遷移表で検証 |
| FR-08 | コメント本文 | 必須、前後空白除去後 1～2,000 文字、改行可 |
| FR-04・FR-05 | ページ番号 | 省略時 1、指定時は正の整数。件数はサーバー側で 20 件固定。範囲外のページは空一覧 |
| FR-09 | 表示名・役割 | 初期データで表示名は 1～50 文字、役割は社員 / IT担当者のいずれか。メールアドレスは一意 |

文字数は Unicode コードポイント単位で数え、日本語を含む値をサーバーでも検証します。必須文字列の空文字、型違い、上限超過を拒否し、勝手に切り詰めません。タイトル・内容・コメント等は空白だけの値も拒否します。パスワードは加工せず上表どおり照合します。本文・コメントはプレーンテキストとして表示し、HTML / Markdown の解釈は行いません。

業務データとして受け付ける項目を操作ごとに限定します。依頼登録に `requester_id`・`assignee_id`・`status`・`role`、コメントに `author_id`・`role` などの保護項目を追加してもサーバー側で拒否し、書き換えません。ログイン要求に `role` を追加した場合も 403 とし、利用者が役割を選んでログインする仕組みにはしません。依頼者・投稿者は認証情報から、ID・日時はサーバーで設定します。認証・CSRF・競合検知に必要な制御項目は設計時に別途定義し、業務データへ一括代入しません。

## 受け入れ条件（提案・すべて未実施）

社員 A・B、IT担当者 X・Y の別アカウントを使い、API の直接呼び出しと DB の変更有無を確認します。UI の確認だけでは合格にしません。API の URL や方式は技術選定後に設計します。

共通のエラー契約案：保護 API への未認証アクセスは 401、閲覧不可の依頼・コメントと不存在は同じ 404、閲覧可能な対象への操作権限違反や保護項目の追加は 403、入力違反は 422、状態条件違反・競合は 409。保護 API の判定は認証 → 対象の閲覧可否 → 操作権限 → 入力・状態条件の順とし、情報を漏らさずデータを変更しません。ログインは未認証で利用でき、入力検証・資格情報の照合を行います。提供しない操作の API は設けず、試行しても 404 / 405 等で拒否し、成功にしません。画面では未認証時にログインを案内し、それ以外は原因に応じた案内を表示します。

| 条件 ID | 関連要件 | 前提・操作 | 期待結果 |
| --- | --- | --- | --- |
| AC-01 | FR-01 | 各役割の初期アカウントで正しい資格情報を入力 | ログインに成功し、役割に合う一覧を表示。応答にパスワード・ハッシュを含めない |
| AC-02 | FR-01 | 誤ったパスワード、または不存在アカウントでログイン | どちらも同じ認証失敗の案内で 401。存在の有無を明かさず、ログイン状態を作らない |
| AC-03 | FR-02 | ログイン後にログアウトし、元の認証情報で保護 API を再要求 | ログアウト成功後は 401。認証情報なしでの再ログアウトは正常終了してもよいが、認証状態を作らない |
| AC-04 | FR-03 | A が正しい 3 項目で登録。IT担当者でも同じ登録を試行 | A の操作では A が依頼者、未対応、担当者なしの依頼が 1 件でき、詳細を表示。IT担当者の操作は 403、依頼は増えない |
| AC-05 | FR-01・FR-03・FR-08 | 必須の欠落、空白だけ、型違い、最大長超過、未定義の種別を送信 | 422 で拒否。空白だけのパスワードは照合対象として扱い、不一致なら 401。最大長ちょうどの妥当な入力は入力検証を通る |
| AC-06 | FR-04・FR-05 | A・B が一覧と詳細を表示し、X・Y も同じ依頼を表示 | A・B は自分の分のみ、X・Y は全依頼を閲覧。0 件・20 件・21 件で件数、ページ、順序を確認。コメントにも同じ境界を適用 |
| AC-07 | FR-03～FR-08 | 未認証で保護 API に直接アクセス | すべて 401。本文・コメント・担当候補を取得できず、DB に変更なし |
| AC-08 | FR-04・FR-05・FR-08 | A が B の依頼 ID・コメント ID を URL や要求本文に指定して閲覧・投稿を試行 | 404。本文、投稿者、件数など B の情報を返さず、コメントも増えない。一覧の条件改ざんでも B のデータを返さない |
| AC-09 | FR-01・FR-03・FR-06～FR-08 | 社員が担当・状態の更新 API を直接呼ぶ、登録・コメントに他人の ID や role 等を付加する | 自分の依頼でも 403、DB の担当・状態・依頼者・投稿者・役割は不変。ログイン要求に role を追加しても 403 となり昇格できない |
| AC-10 | FR-06 | X が未対応の依頼に Y を割り当て、別の IT担当者へ変更、解除する | 成功し、状態は未対応のまま。社員・不存在の ID は 422、対応中・確認待ちの解除と完了後の変更は 409 |
| AC-11 | FR-07 | X または Y が遷移表の各遷移を行う | すべて許可条件どおり成功し、担当者を保持。未割当の対応開始、飛び越し、同じ状態、完了からの再開は 409 |
| AC-12 | FR-08 | A と X・Y が A の完了前の依頼へ投稿する | 各投稿者が認証中の本人として記録され、閲覧可能者だけに表示。完了後は依頼者・IT担当者とも 409、投稿なし |
| AC-13 | FR-03・FR-05・FR-08 | 本文やコメントに HTML タグ・スクリプトを模した文字列を含める | 文字列として表示し、スクリプト実行や他の利用者の画面改変が起きない |
| AC-14 | FR-06～FR-08 | 同じ版から担当・状態を同時更新する。または完了確定後に投稿が確定しようとする | 古い版の更新と完了後の投稿を 409 で拒否し、更新の上書きや完了後コメントが発生しない |
| AC-15 | FR-03・FR-05・FR-08 | 社員・IT担当者が依頼やコメントの編集・削除、役割変更を試みる | 対応する操作は提供されず、直接要求も拒否。元のデータ・役割が変わらない |
| AC-16 | FR-09 | 開発・検証用の空 DB に初期データを投入し、再実行する | 社員 2 人・IT担当者 2 人、3 種別と 4 状態を含む架空の依頼 4 件以上とコメントを用意。A・B のデータ分離を実演できる。再実行で重複・既存内容や資格情報の上書きをしない |
| AC-17 | FR-09 | 本番向け環境でデモ初期データ投入を試行する | デモ投入を拒否。環境判定方法は設計時に決める。実在データ・固定の公開パスワードを Git やイメージに含めない |

初期データの資格情報は環境準備時に安全な経路で与え、パスワードはハッシュ化して保存します。初期データは UI の受け入れ例であり、秘密情報検査用の疑似トークンは含めません。業務トランザクションが失敗した場合は部分的な保存を残さないことも確認します。

## 扱うデータ・保存と削除（提案と検討事項）

以下は論理的なデータ項目案であり、テーブル構成・型・ID 方式を確定するものではありません。

| データ | 主な項目・関係 | 保存・削除で検討すること |
| --- | --- | --- |
| アカウント | ID、表示名、ログイン用メール、パスワードハッシュ、役割。1 人が複数の依頼・コメントに関連 | 平文パスワードを保存しない。退職・資格情報漏えい時のアクセス停止と、過去の依頼・投稿者表示を残す方法を公開前に決める |
| 依頼 | ID、依頼者、タイトル、内容、種別、担当者（任意）、状態、作成・更新日時、競合判定用の情報 | 完了しても直ちに削除しない。完了後の保存期間、誤って機密情報を入力した場合の修正・削除手順と実施者を決める |
| コメント | ID、依頼 ID、投稿者 ID、本文、投稿日時 | 親依頼と同じ閲覧権限。依頼の運用削除時に一緒に削除するか、匿名化して残すかを決める |
| 認証状態 | ログイン中の本人・期限・失効に必要な情報（方式は未決定） | ログアウト時の失効、有効期限、期限切れデータの削除時期を決める |
| 初期データ | 架空の利用者・依頼・コメント。資格情報はソース外から提供 | 開発・検証環境限定。公開デモに流用するかは公開方法と合わせて判断し、データのリセット範囲・頻度・実行者を決める |
| ログ・バックアップ | 認証・操作の結果、必要最小限の識別情報、復元用データ | 本文・コメント全文、パスワード、認証情報を通常ログへ出さない。閲覧権限、保存期間、バックアップ上の削除反映・復元確認を決める |

初期版では不要な住所・電話番号等を収集しません。依頼・コメントにパスワード、API キー、実在の顧客情報などを記入しない案内を設けます。自由記述の機密性は入力者任せにせず、認可・ログ制御でも保護します。

保存期間・削除実行者・アカウント停止手順は**未決定**です。画面の削除機能が対象外でも無期限保存を確定したことにはしません。実在データを扱う運用に進む前に決定し、データ・バックアップ双方で実行可能な手順を定めます。

## 技術選定の観点（最終選定は未決定）

| 対象 | 候補 | 比較する観点 |
| --- | --- | --- |
| フロントエンド | React を中心とする構成 / Next.js | レンダリング・SEO の必要性、ルーティング、配信方法、バックエンドとの責務分担、学習・運用負荷 |
| バックエンド | Laravel / FastAPI | PHP / Python の習熟度、認証など必要な機能、DB 操作・マイグレーション、テスト、保守性 |

選定時には「必要な要件 → 候補の比較 → 採用理由 → 制約・見送った理由」を記録します。実測していない性能や費用を選定根拠として断定しません。

AWS ECS、Terraform、GitHub Actions、PostgreSQL、Docker の使用は決定済みです。一方、ECS の起動方式、DB の配置、入口・TLS・ドメイン、ネットワーク、リージョン、常時稼働の有無は未決定です。月額見積もりでは計算資源だけでなく、DB、入口、通信、ログ、イメージ・状態ファイルの保存なども含めます。

## 開発と受け入れの進め方（提案）

1. 決定済みの題材について、今回の初期機能・権限・遷移・データの案と、受け入れ条件・脅威分析をレビューする。
2. 予算・公開方法を踏まえて技術を選定し、データモデル・API・権限・構成を小さく設計する。
3. Docker での開発手順と CI の検査を整え、一つの利用シナリオずつ実装・検証する。
4. 公開前にセキュリティ、デプロイ・復旧手順、費用見積もりを確認する。

機能の完了条件案：受け入れ条件に対応したテストを通し、関連する検査結果・変更理由・残る制約を説明できること。必要な検査が失敗または未実施なら、検証済みとして扱いません。具体的なリリース条件は公開前に決定します。

## 意思決定と検証の記録（提案）

意思決定には日付、対象要件、候補、採用理由、不採用理由、制約、見直す条件を残します。検証には対象コミット、環境・ツールバージョン、手順、期待結果、実際の結果、証跡、未実施の理由を残します。保存場所は未決定です。

面接では、要件を一つ選び「なぜ必要か」「なぜその設計か」「どう確かめたか」「何が未解決か」を一続きで説明できる状態を目指します。

## 今回レビューしてほしい重要事項

1. **権限の分担**：依頼登録は社員のみ、すべての IT担当者が全依頼を担当外も含めて変更できる案でよいか。
2. **完了と訂正の扱い**：完了は IT担当者の判断、社員の承認は必須化せず、編集・削除・完了後コメント・再開は設けない案でよいか。
3. **入力とデータ運用**：文字数上限・初期データ案が十分か。保存期間、資格情報の配布・失効、誤投入時の削除を公開前にどう決めるか。
